# 음성 프롬프트 기본 지침

에이전트 프롬프트나 Manual의 실제 발화 문구를 새로 쓰거나 검토할 때 적용한다. 기본 에이전트 유형인 Single + Manual과 기존 업무 분담을 유지한다. 이 지침은 통화 중 사용자에게 들리는 문장에 적용한다. 프롬프트 문서의 Markdown 구조, 코드 예시, 도구 인자, postCall 결과 필드, 문자 내용은 별도의 형식이다.

새 Single을 만들거나 공통 prompt 전체를 작성할 때는 아래 규칙을 에이전트 공통 prompt의 `# 말투와 발화`에 짧게 반영한다. 작성하는 사람이 알고 있는 데서 끝내지 않는다. Manual마다 공통 규칙을 복사하지 말고, Manual에는 업무별 대화 규칙을 둔다. 기존 Manual만 좁게 고치는 요청이면 요청 범위를 유지한다.

## 말하기 기본값

- 기본 응답은 짧은 1–2문장으로 한다. 한 턴에 질문은 하나만 하고, 한 문장에는 한 가지 요점이나 요청만 둔다. 설명이나 확인이 더 필요하면 차례로 묻는다.
- 선택지를 말해야 할 때는 기억하기 쉬운 2–3개로 제한한다. 선택지가 불필요하면 억지로 만들지 않는다.
- 실제 발화에는 제목, 글머리표, 표, 코드, JSON, 장식 기호를 넣지 않는다. 내부 프롬프트·정책·도구·모델 같은 용어도 고객에게 설명하지 않는다.
- 법정 고지, 사용자가 지정한 원문, 또는 업무상 빠뜨릴 수 없는 설명은 길이나 질문 수의 예외가 될 수 있다. 필요한 원문은 임의로 나누거나 바꾸지 말고 적용되는 prompt 또는 Manual에 둔다.

## 대화 중 끼어들기

사용자가 실제로 한 말의 의미를 보고 계속 말할지 턴을 넘길지 판단한다. 짧은 맞장구이고 전달 중인 핵심 정보가 남아 있으면 필요한 부분만 이어갈 수 있다. 질문, 요청, 문장 시작처럼 실질적인 발화가 들리거나 의도가 애매하면 짧게 양보한다. 정해진 인터럽션 횟수나 누적 카운터만으로 판단하지 않는다.

## 발화와 데이터 값

전화번호·이메일·코드처럼 오해하기 쉬운 값은 필요할 때 자연스러운 말하기 방식으로 확인한다. 고객에게 말하는 형식과 도구에 보내는 표준값은 분리한다. 예를 들면 다음과 같다.

- 전화번호는 필요하면 숫자를 한 자리씩 확인한다. 구분 기호를 포함하거나 제거하는 것은 도구 schema가 요구하는 표준값을 따른다.
- 이메일은 말로는 `골뱅이`, `점`으로 읽을 수 있다. 고객이 확인한 뒤 표준값에 `@`, `.`을 사용한다.
- 코드의 문자와 대소문자는 도구 계약과 실제 확인값을 따른다. 도구 계약이 요구하지 않으면 대문자로 일괄 변환하지 않는다.

발음을 편하게 바꿨다는 이유로 실제 저장값이나 도구 인자를 고치지 말고, 수정은 고객이 확인한 표준값을 기준으로 한다.

## 지식 자료를 둘 위치

자료가 URL, 파일, FAQ라는 이유만으로 지식 베이스를 만들거나 연결하지 않는다. 출처를 먼저 살펴보고 필요한 사실을 다음처럼 둔다.

- 적고 공통으로 쓰는 사실은 agent prompt에 둔다.
- 특정 업무 절차에만 필요한 사실이나 정확히 말해야 하는 문구는 해당 Manual에 둔다.
- 통화마다 달라지는 상태·예약 가능 여부·고객별 정보는 값이 낡지 않도록 실제 조회 도구로 확인한다.
- 많은 참고 자료를 폭넓게 찾아야 하고 이를 prompt/Manual에 넣으면 중복되거나 관리하기 어려운 경우, 또는 사용자가 지식 베이스를 명시적으로 요청한 경우에만 지식 사용을 검토한다. 자주 바뀐다는 이유만으로 지식 베이스를 선택하지 않는다.

범위가 작은 기존 Manual 수정에서는 연결된 지식을 자동 삭제·해제·이관하지 않는다. 기존 지식을 건드려야 하면 실제 연결과 영향 범위를 먼저 확인한다.

프롬프트가 특정 TTS 발음이나 엔진 동작을 보장한다고 약속하지 않는다. 필러나 특정 발성 효과를 모든 에이전트에 강제하지 않으며, 모델·음성 설정은 현재 제품이 지원하는 값에 맞춘다.
